## 1. 产品形态与整体路线

服务不会编程的个人创作者，让 AI 从描述生成小型游戏，并在同一项目里持续修改。

用户流程：**一句话 → 方向 → 人物与动作 → 场景 → 核心试玩 → 完整游戏 → 交付。**每步先看成果再确认。

开发采用“每次做出一个能操作的小环节”：在原有桌面界面接上当前能力，让用户能看、能改、能确认。现有正式组件优先复用，不另造一套网站；每次只补当前节点所需的界面，整体视觉打磨留到阶段 3。

首发仍为 macOS 本地桌面；游戏使用 Godot 4 的 2D 工程，并导出网页游戏包。公网托管、手机 App、3D 和多人功能不在本轮。

## 2. 技术方案：每一部分负责什么

| 部分 | 采用什么 | 产品作用 |
| --- | --- | --- |
| 操作界面 | 原有 Electron + React + TypeScript | 显示方向卡、人物、场景、试玩和修改入口 |
| AI 调用 | 原有 Codex App Server，模型沿用应用设置 | 理解要求、生成游戏代码、继续修改；不擅自更换模型或服务商 |
| 图片与音效 | 原有素材服务接入 | 生成、保存、预览素材；具体可用路线到对应节点核验 |
| 游戏运行 | Godot 4 与匹配的网页导出模板 | 运行人物动作、碰撞和玩法，提供真实试玩 |
| 流程控制 | 桌面主进程中的确定性代码 | 决定当前可做哪步，保存用户确认，拦截重复和过期操作 |
| 保存与恢复 | 本地流程文件、素材文件与工程版本 | 保存成果、确认和任务；失败不损坏上一版 |

**AI 负责创造与修改，程序负责保存、检查和等用户确认。**程序不会用几个预设数值代替 AI 游戏开发；AI 也不能自己决定“用户已经同意”。

### AI 怎么分工

沿用原项目的三种职责，不为每个页面额外创建一个 Agent：

- **规划**：把当前要求拆成具体任务，说明要使用的已确认内容；只读。
- **制作**：生成或修改当前候选工程及素材；只能在允许的工程范围内工作。
- **审查**：独立检查当前成果，再由平台运行文件、引擎和试玩检查；不能自行替用户确认。

方向卡只需要文字规划，不启动完整制作循环、图片生成或 Godot。人物阶段才接图片与动作；玩法阶段才编写和运行实际游戏。每步的输入包含用户需求、当前修改、已确认上游成果和当前交付要求；提示词分别维护。

### 用户确认怎样真正控制过程

1. 平台检查当前阶段、成果版本及是否已有任务在运行。
2. AI 只接到当前任务，在单独的候选版本中工作。
3. 平台检查输出；通过后显示“待确认”，停止后续生成。
4. 用户确认当前版本，平台保存记录，才允许已开放的下一步。

开发尚未验收的节点不能被界面或模型调用提前开放。例如节点 2-1 的交付版本，确认方向后只保存方向，不生成人物。等人物节点完成验收，才开放这段衔接。这是开发中的交付边界，最终产品仍按完整创作流程推进。

## 3. 复用范围与需要补齐的能力

| 已有基础 | 处理方式 | 尚不能当成已完成的部分 |
| --- | --- | --- |
| Noobi.ai 的账户、模型会话、规划/制作/审查、预览与素材管理 | 保留接口和合理结构，按当前创作任务调整输入与检查 | 原流程面向完整游戏，不能原样用于“只做人物” |
| 原有 Godot 工程创建、检查及网页导出 | 复用，按节点检查环境 | 起始工程没有现成的完整横版或俯视玩法 |
| 已写方向卡、阶段控制、保存和修改草稿 | 节点 2-1 先审查，再修复和验证，避免重写 | 离线示例和历史测试不证明真实 AI 已可用 |
| 已写人物/场景/版本模块草稿 | 保留冻结，到对应节点再复用 | 不提前联调、不作为后续节点验收通过 |
| 原有角色装饰动画与素材工具 | 可复用处理环节 | 不等于任意游戏角色都能生成一致、可玩的动作 |

新增重点是：成果卡及真实预览、用户确认记录、上游版本继承、改动影响说明和整体恢复。图片与玩法由 AI 生成；固定模板只能帮助搭建基础，不能限制用户只改几个预设参数。

### 保存和接口安排

- 项目记录、阶段成果、任务状态、用户确认和历史版本保存在本机；采用带格式版本的结构化文件与原子写入，当前无需云数据库。
- 权威确认记录放在应用数据目录，与 AI 可编辑的候选工程分离；AI 输出不能伪造用户确认。
- 每次操作携带项目、操作标识与成果版本；重复点击不产生两次生成，旧版本不能确认新版。
- 界面继续通过受控桌面接口读取流程、提交修改、确认、停止和恢复，不直接拿到文件写入或凭据权限。
- 修改先展示影响；新候选检查通过才替换当前版本。旧快照保留，恢复同步还原工程、素材和确认状态。
- 中断后恢复已有内容并标明未完成任务；不自动重启可能产生费用的调用。每次生成重建所需上下文，避免恢复后继续使用错误的旧要求。

## 4. 技术取舍、费用和本轮不做的事

| 取舍 | 原因与影响 |
| --- | --- |
| 延续桌面技术，不新建 Python 后端或网页产品 | 已有项目能承接需求；不为套用手册迁移工程 |
| 当前节点带最小真实界面，阶段 3 再整体打磨 | 确认与预览属于核心能力；保留的界面从首次交付起就检查构建、交互和窄窗口 |
| 数据与任务先保存在本机 | 首版是个人本地制作，暂不引入云数据库、多人协作或额外平台登录 |
| 暂缓公网分享、签名公证和正式分发 | 先交可核验的本地测试版本；不创建付费云资源或开发者账户 |
| 保留原项目中其他引擎的代码，新入口只开放已定 2D 范围 | 不删除原有功能，也不承诺交付其他引擎与 3D |

**费用按当前节点处理：**先完成该节点不产生新费用的实现和本地检查，再提交该节点的真实测试范围、调用数量和费用上限。未获费用授权，停在该节点“待真实验证”；不能继续铺后面的功能。

本轮方案不调用模型，不新增付费服务。实际账号、模型和图片路线尚未连通验证，不填虚构单价或工期。原制作循环包含最多 3 轮修复；后续复用时必须把重试纳入获批预算，不能将“复用”理解为默认获得付费重试授权。

已对账：手册允许沿用既有项目、在核心交互节点保留最小界面；与强制底线无冲突。默认网页/云部署不适用于已确认的桌面范围。逐节点验收不能因费用安排或已有草稿而合并取消。

### 每个节点都怎么验收

1. **程序检查**：正常路径、失败、重复提交、过期确认、中断及真实进程重启恢复；旧节点必要回归；实际工程的类型检查与构建。
2. **真实 AI 与引擎**：在授权费用范围内实际生成和修改，保存真实调用记录；有动作或游戏时必须真正运行。示例数据不能代替。
3. **用户体验**：交可打开的当前节点界面、简短操作步骤和通过标准；用户看内容是否符合预期，有试玩就亲自操作。
4. **节点放行**：检查证据齐全、待验项关闭，并得到用户明确验收后，才进入下一节点。检查通过不自动视为用户通过。

保留界面均检查桌面和窄窗口；没有手机产品承诺。自检必须连接真实 Noobi.ai 工程，不能因工具包内没有 backend/frontend 目录而跳过。旧自检适配与离线入口也是未验收草稿，留待节点 2-1 核验，本阶段不改脚本或运行产品测试。

### 会影响成败的三处

- **人物动作一致性**：图片看着相似、文件里出现动画名称，都不能证明动作可用。节点 2-3 要实际播放移动、攻击/跳跃并对照选中人物；未通过就停在此节点修复。
- **改动后的继承与恢复**：只做文件快照还不够；要证明回退后角色、玩法、确认记录一致。当前节点从一开始保存版本，节点 2-9 再验证跨阶段联动。
- **实际生成成本与效果**：方向、图片、游戏代码、审查的费用和失败率不同；按节点测，不承诺“一次一定生成成功”。账号或引擎未就绪时如实待验。

## 7. 分节点开发计划

下表是未来开发顺序，不表示已经开工。每行都是独立开发与验收节点；本阶段不提前编写这些节点的实施文档。

| 节点 | 本节点交付 | 你怎么验收 | 本节点边界 |
| --- | --- | --- | --- |
| 2-1 方向卡 | 输入想法→AI 方向卡→自然语言修改→确认→保存和恢复 | 改成手动攻击，卡片正确更新；确认后停止；重开和恢复内容仍在 | 不生成人物、场景或游戏 |
| 2-2 人物候选 | AI 生成两个候选，可局部修改、选择与保存 | 改衣服但保留发型/武器，选中的人物版本确实保存 | 不做动作或场景；选中只表示决定人物基础 |
| 2-3 人物动作 | 选中人物的真实移动、攻击或跳跃预览 | 动作可播放、人物一致；两个游戏视角都核对；动作确认后才允许后续 | 不做场景和关卡 |
| 2-4 场景 | AI 场景与已确认人物组合，可修改 | 背景变化而人物保持；比例和视角适合所选玩法 | 不做完整敌人/关卡 |
| 2-5 横版核心试玩 | 可操作的跑跳小样，AI 能新增行为 | 提出“落地恢复的二段跳”，实际试玩生效 | 不扩成完整多关游戏 |
| 2-6 俯视核心试玩 | 可移动、攻击的小样，AI 能新增行为 | 提出“剑气碰墙反弹一次”，实际试玩生效 | 不补齐整局波次和成长 |
| 2-7 横版完整小局 | 在已确认试玩上补进展、胜负、暂停、重开与必要音效 | 从开始玩到结束，再重开一局；人物与玩法不被换掉 | 只完善横版，不顺带做俯视整局 |
| 2-8 俯视完整小局 | 在已确认试玩上补波次、升级、胜负、暂停、重开与必要音效 | 打完一局、升级和重开正常；可用语言调整难度 | 只完善俯视，不扩展新类型 |
| 2-9 跨阶段修改与恢复 | 连接前面各节点已有的版本，完成改动影响及整体恢复 | 完整游戏里改衣服，玩法保持；恢复旧版后外观与确认一致 | 不同时做导出与安装包 |
| 2-10 游戏交付 | Godot 工程与网页游戏包、真实运行核验 | 导出包可运行且与最后确认版本一致 | 不托管成公网分享链接 |
| 3-0 体验方案 | 确定已有页面的统一视觉、引导和错误呈现 | 看代表页方案和交互说明 | 只出方案，确认后再改界面 |
| 3-1 桌面体验完善 | 在现有组件上完善中文、等待、错误、首次配置和窄窗口 | 小白独立完成制作、修改、恢复 | 不新增玩法与云服务；前端手册其他界面轮次合并于此，细节在 3-0 定 |
| 3-2 Mac / Windows 测试包 | 本地安装或解压启动、环境引导与跨平台导出 | 分别在 Mac 与 Windows x64 上走完主流程；签名与待验状态如实说明 | 2026-11-09 用户追加 Windows 适配；不购买签名/公证服务，不公开发布 |
| 5 收尾 | 使用、启动、恢复与接手文档，已验收/待处理清单 | 能照说明使用和接手 | 本轮跳过阶段 4 公网部署 |

### 为什么这样拆

人物图与人物动作的难点不同，所以分别交付；横版与俯视的操作和规则不同，所以试玩与完整小局分别验收。通用方向、人物、场景和保存能力共用，不重建两套平台。每个相关节点同时检查两类所需的视角和素材约定，避免后做一种时推翻前面的数据。

保存、重开恢复和当前成果修改从节点 2-1 起就是基本要求；节点 2-9 是跨阶段综合验收，不意味着前面可以不保存、不能修改。

计划变更先更新本节并记录原因；涉及节点合并、范围、费用或用户验收方式改变时，先取得用户同意，不先做后告知。
