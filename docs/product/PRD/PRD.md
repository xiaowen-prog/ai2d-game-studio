# AI 2D 游戏制作平台｜分阶段共创需求文档 V1

> **产品定位：面向编程小白，让 AI 分阶段制作 2D 游戏。每一步先交出用户能看、能试的成果，用户确认或修改后，再继续制作。**
>
> **首版范围：支持2D横版闯关和俯视打怪，题材不限。AI 生成和持续修改是核心能力。**
>
> **主流程：一句话需求 → 简短方向确认 → 人物 → 场景 → 核心试玩 → 完整游戏 → 检查交付。**
>
> **复用判断：保留 Noobi.ai 的 AI、素材、引擎、预览和检查能力，重点新增阶段确认、成果版本和返回修改机制。不是只给进度条增加按钮。**

- 文档状态：2026-11-05 阶段 0 已确认；当前进入阶段 1 方案审阅，尚未验证新流程的实际生成效果。

## 1. 背景、目标用户与核心价值

### 1.1 为什么做

Noobi.ai 已经支持自然语言生成游戏、继续修改、素材生成、预览和自动检查，也有制作进度展示。现有主要执行流程是 AI 规划后进入实现，再审查和修复。

本产品要补上的是：**把关键创作成果交给用户决定，再将已确认的内容用于下一步。**例如先确认白衣侠客，再确认侠客所在的竹林，再试玩战斗，最后形成完整短局。

预期收益是让用户更早发现“做偏了”，减少整款游戏做完后才重来的情况。该收益仍需通过真实用户任务验证，不能由“确认按钮更多”直接推导。

### 1.2 服务谁

- 主要用户：不会写代码、但有游戏创意的个人创作者，包括游戏爱好者和策划、美术背景的人。
- 用户任务：通过描述、选择和试玩，完成自己的小型游戏，并在同一项目里持续修改。
- 首版不面向大型商业游戏、复杂既有工程改造或多人协同开发。

### 1.3 与原项目的具体差异

| 比较点 | Noobi.ai 已有基础 | 本产品新增目标 |
| --- | --- | --- |
| 制作过程 | 已有进度展示，AI 在规划、实现、审查之间推进 | 人物、场景、试玩等成为独立成果；用户确认后推进 |
| 用户修改 | 已能继续对话修改，能重新生成素材 | 修改明确归属到某个阶段和版本，说明对后续的影响 |
| 结果继承 | 已有项目文件、素材记录和持续会话 | 保存“用户确认的是哪一个成果”，后续必须沿用 |
| 交付范围 | Web 与 Godot，覆盖多种游戏需求 | 首版集中交付两类 2D 单人小型游戏 |

**“能用 AI”“能继续修改”“有预览”都是复用能力；分阶段交付、确认和返工衔接才是这次改造重点。**

## 2. 首版范围与优先级

### 2.1 P0：首版必须有

| 范围 | 首版要求 |
| --- | --- |
| 游戏类型 | 支持2D横版闯关和俯视打怪，题材不限 |
| 创作入口 | 一句话需求；可附角色或风格参考图；补齐影响制作的少量关键选择 |
| 分阶段制作 | 方向、人物、场景、核心试玩、完整游戏、交付都有明确成果和状态 |
| AI 能力 | 生成角色与场景、生成或修改游戏行为、完成素材接入和检查；不局限于改文案或填数值 |
| 用户控制 | 确认继续、提出修改、重试失败任务、返回前面调整、恢复已保存版本 |
| 连续性 | 已确认角色和场景进入后续游戏；关闭项目后能恢复到原阶段 |
| 真实反馈 | 人物阶段展示真实动作预览，玩法阶段提供可操作的小样 |
| 完整交付 | 开始、游玩、进展、胜负、重新开始均可用；交付工程和经过检查的网页游戏包 |

以下是本版建议的规模边界，作为默认制作上限：

- **横版闯关：**1 个主角、1 套场景风格、最多 3 个短关卡，围绕跑跳、收集、障碍和终点制作。
- **俯视打怪：**1 个主角、1 张地图、2 类敌人、最多 2 种攻击方式、3 项局内升级、3 波敌人。
- 默认选择一种基础美术风格；每个项目允许 AI 在上述范围内新增具体行为，例如二段跳、踩踏后消失的平台、剑气反弹。
- 超出范围时，先说明并给出可制作的缩小方案，由用户选择；不能默默删需求。

### 2.2 P1 与暂不做

| 优先级 | 内容 |
| --- | --- |
| P1 | 一键托管和公网试玩链接、版本并排比较、更多角色与关卡、更多动作、益智等新类型 |
| 暂不做 | 3D、多人联机、开放世界、庞大剧情或经营系统、任意旧项目导入、自动判断“好不好玩” |
| 界面暂不做 | 自由拖线的复杂工作流画布、让用户配置 Agent、模型链或制作脚本 |

### 2.3 首发交付方式

为控制改造量，本版建议沿用本地桌面应用，先覆盖原项目已有的 macOS 路线；内部以 Godot 4 的 2D 工程运行两类游戏，用户不需要选择引擎。

- 首版提供可安装的测试版本、必要环境的检测和引导，用户不应自行下载源码或执行命令。
- 模型账户或服务配置可沿用原项目，缺失时用中文说明并保留创作草稿；不承诺首版无需任何账户配置。
- 游戏交付为 Godot 工程与网页游戏包，并在应用内试玩。
- **网页游戏包不等于已上线的分享链接。**公网托管作为 P1；首版不承诺直接双击网页文件即可运行，也不承诺 Windows/macOS 原生游戏安装包。

## 3. 每一步 AI 做什么、用户看什么

贯穿示例：用户输入“我想做一个武侠类的肉鸽游戏”。

### 阶段 0：把一句话变成简短制作约定

- **AI 做什么：**提出适合首版的理解，例如“2D 俯视角，玩家移动，侠客自动攻击，击败三波敌人，每波结束选升级”。明确画面视角、主要操作、目标和本次规模。
- **给用户看什么：**一张短卡片，写明“怎么玩、长什么样、这次做多少”；不要求用户阅读长篇策划书。
- **用户怎么确认：**点击“按这个方向开始”，保存约定并进入人物阶段。
- **用户怎么修改：**直接说“我想手动攻击”或更换游戏类型。存在会改变后续制作的关键缺口时，集中问一两个容易回答的问题。
- **完成条件：**用户理解并确认基本方向。此时不提前生成角色、场景或完整游戏。

### 阶段 1：生成并确认人物

- **AI 做什么：**按已确定的视角和风格生成 2 个主角候选。用户选中一个后，制作这个角色的基础移动与攻击动作；横版项目对应移动与跳跃动作。
- **给用户看什么：**候选人物图、简短特点，以及选中角色真实的动作预览。图片出现时即可展示，未完成的动作明确标注“制作中”。
- **用户怎么确认：**候选选择只表示“基于这个继续做动作”；动作完成后，点击“确认人物，继续场景”才通过本阶段。
- **用户怎么修改：**对选中人物说“衣服改白，保留发型和武器”；重新生成受影响内容，保留上一版供恢复。
- **完成条件：**最终人物图与动作使用同一形象；用户确认的是一个确定版本。后续游戏使用这一角色，不能另换一个相似人物。
- **首版限制：**只做一个可玩主角的基础动作；多套成长外观、多职业角色作为后续扩展。

### 阶段 2：生成并确认场景

- **AI 做什么：**生成 1 套场景画面，把已确认角色放入实际游戏视角，检查大小、位置和辨识度。
- **给用户看什么：**角色站在竹林中的场景预览，说明当前确认的是画面与空间方向，完整敌人和关卡尚未制作。
- **用户怎么确认：**点击“确认场景，继续玩法”。
- **用户怎么修改：**说“竹林改成雪山，人物保持不变”或“背景亮一点”；只更新受影响内容。
- **完成条件：**展示可实际用于游戏的画面组合，保存素材与布局版本。不能仅展示一张漂亮概念图，最终游戏却使用无关素材。

### 阶段 3：制作并确认核心试玩

- **AI 做什么：**依据制作约定给出简短玩法说明，接入已确认的人物和场景，做一个约 30–60 秒可体验核心操作的小样，并检查运行与关键规则。
- **给用户看什么：**真正能操作的窗口、按键说明、当前已实现内容。例如能移动、挥剑、击败敌人，并试用一次升级；横版项目能跑跳、收集、遇到障碍并到达目标。
- **用户怎么确认：**亲自试玩后，点击“确认玩法，制作完整游戏”。
- **用户怎么修改：**说“剑气碰墙反弹一次”或“兔子能二段跳”；AI 修改实际游戏，展示本次变化，再让用户试玩。
- **完成条件：**操作与反馈真实存在，修改要求在小样中能观察到；已确认美术被使用。预录视频不能代替本阶段的可玩成果。

### 阶段 4：制作并确认完整游戏

- **AI 做什么：**在核心试玩基础上补齐短关卡或敌人波次、升级选择、开始与结算界面、基础音效、暂停和重新开始；保持已确认的玩法和画面。
- **给用户看什么：**一局可以从头玩到结束的游戏，以及本阶段增加了什么。
- **用户怎么确认：**试玩后点击“确认完整游戏，检查交付”。
- **用户怎么修改：**说“第二波太难，减少冲撞敌人”或“最后一关多加一个移动平台”；AI 更新对应内容并重新检查。
- **完成条件：**完整游玩过程可走通，胜负与重开正常；用户确认当前版本。AI 检查运行正确性，手感与是否喜欢由用户试玩判断。

### 阶段 5：检查与交付

- **AI 与系统做什么：**检查完整流程，修复技术错误，生成网页游戏包，并检查导出的包能运行。保存工程、素材与阶段记录。
- **给用户看什么：**交付版本的试玩入口、简短检查结果、工程与游戏包位置、已知限制。
- **用户怎么确认：**试玩交付版本后点击“确认完成”。只有检查通过且用户确认，项目才标为“已完成”。
- **用户怎么修改：**选择“继续修改”，回到对应创作阶段；已交付版本保留，新修改形成新版本。
- **完成条件：**交付文件真实存在且能运行。技术修复如果改变了用户已确认的外观或玩法，必须返回相应阶段重新确认。

## 4. 统一交互规则

### 4.1 页面与按钮

首版采用简单阶段列表，不做复杂画布：左侧显示阶段与状态，中间展示当前成果，下方输入修改要求；已确认阶段可查看。

| 操作 | 规则 |
| --- | --- |
| 确认并继续 | 绑定当前成果版本；先保存确认，再启动下一阶段。同一次确认重复点击不会重复生成 |
| 提出修改 | 默认作用于当前阶段及明确选中的对象；生成新候选版本后重新等待确认 |
| 换一个／重新生成 | 保留上一版，只重做指定成果；与失败任务的“重试”区分 |
| 返回前面调整 | 先展示会影响哪些后续成果，经用户决定后再执行 |
| 恢复版本 | 恢复所选阶段结束时的一整套一致状态；后续较新的修改留在历史里，不混入恢复版本 |
| 停止制作 | 尽快停止后续任务，保存已确认内容；正在执行的外部生成不承诺立即取消或退费 |

按钮确认和含义明确的自然语言确认均有效，例如“这个版本可以，继续”。“不错，但衣服换成蓝色”属于修改，不属于通过。

### 4.2 确认必须真实控制制作

- 未确认时，不启动依赖该成果的后续生成、修改或付费任务。
- 关闭页面、超时或没有回答，都不等于确认。
- 系统记录确认的阶段、成果版本、时间和关联素材。AI 自己说“用户已确认”不能替代用户操作。
- 当前版本正在修改时，旧版本的确认入口失效；不能让过期确认推动新版本进入下一阶段。
- 用户确认创作结果，不需要逐条批准普通编程或检查步骤；必要的工具权限审批另行保留。

### 4.3 状态与等待体验

用户可见状态：**未开始、制作中、待确认、已确认、需要更新、制作失败、已停止**。最终交付另有“检查中、待验收、已完成”。

- 制作中显示真实任务，例如“正在生成角色动作”，已产出的图片可先展示。
- 等待动效只表示忙碌；角色动画必须来自当前成果，玩法 demo 必须真实可玩。
- 待确认时，明确显示下一步是什么；不能用进度动画暗示后台仍在偷偷制作下一阶段。
- 失败时说明哪项失败、已有成果是否保留、用户能否重试；不能自动进入下一阶段。
- 每个项目同一时间只推进一个创作任务。重复点击、重开项目不重复发起模型调用。
- 关闭后重新打开，恢复已确认内容和待确认成果；中断的生成标明状态，由用户决定继续或重试。

## 5. 返回修改与版本继承

**原则：保留不受影响的内容，只更新受影响的内容；旧版本始终可查看。**

| 修改例子 | 需要处理什么 | 保留什么 |
| --- | --- | --- |
| 侠客白衣改蓝衣 | 人物画面、相关动作及后续场景／游戏中的显示重新更新与确认 | 战斗规则、关卡规则保留，并重新检查运行 |
| 竹林只改背景颜色 | 更新场景和后续画面预览 | 角色、地图碰撞和玩法规则保留 |
| 场景增加挡路的墙 | 更新场景布局，重新检查移动、攻击和关卡是否可完成 | 无关角色和音效保留 |
| 自动攻击改手动攻击 | 重新确认玩法，更新操作提示、关卡节奏及最终检查 | 可兼容的人物和场景素材保留 |
| 俯视游戏改横版 | 说明视角、动作和关卡需重新制作；建议另建项目保留原作品 | 不静默覆盖原游戏 |

返回修改时，先提示“将更新哪些内容、哪些确认需要重新做”。用户接受后，新版相关阶段标为“需要更新”；其后续依赖必须等待新版确认。不会把旧版确认自动套到新成果上。

修改结果只有完成检查并保存后，才能替换当前成果；失败不能破坏上一份已确认版本。

## 6. Noobi.ai 能复用什么、需要改什么

下面依据当前本地代码判断。**“有现成实现”不等于“新业务流程已经验证通过”。**

| 模块 | 现有基础 | 本版处理 |
| --- | --- | --- |
| AI 调用与持续修改 | Codex 接入、会话继续、事件输出 | 复用；每次只允许完成当前已授权阶段的任务 |
| 规划、实现、审查 | Planner、Implementer、Reviewer 与修复循环 | 复用职责，重写阶段任务和完成标准；不必每个页面新建一个 Agent |
| 图片、音效与素材管理 | 生成、登记、失败记录、单项重试 | 复用；新增候选、用户确认版本、后续引用关系 |
| Godot 与预览 | 工程创建、环境检查、导出、应用内预览 | 复用；增加两类 2D 玩法基础与阶段专用预览 |
| 项目保存 | 项目记录、素材清单、持续会话 | 扩展为阶段成果、确认记录和完整版本保存；会话恢复不等于工程回退 |
| 制作进度 | 已有八个内部制作阶段与进度界面 | 改为用户理解的人物、场景、试玩等创作阶段；内部任务仍可用于诊断 |
| 用户输入与权限审批 | 已有问题输入、命令和文件等审批界面 | 保留必要能力；新增“阶段成果确认”，不能直接把现有审批视为已具备 |
| 自动检查与修复 | 运行、截图、错误与游玩过程检查 | 复用底层能力；按阶段调整要求，再补具体玩法规则的检查 |
| 安装与交付 | 开发者预览和本地构建基础 | 补小白可用的测试安装包与环境引导；公网托管不属于现成复用能力 |

### 6.1 必须新增的五项能力

1. **阶段控制：**真正在阶段结束时停下，等待用户，保存后再继续。
2. **成果卡与真实预览：**把候选角色、动作、场景和可玩小样交到用户面前。
3. **确认内容的继承：**后续明确使用用户选中的版本，防止 AI 擅自重画或改玩法。
4. **版本与影响管理：**保存、恢复，并判断前面修改会影响哪些后续内容。
5. **两类 2D 制作基础：**分别准备横版和俯视游戏的基础能力及验收案例。原项目的中性起始工程不是现成的完整玩法模板。

主要工作量在阶段控制、版本恢复、修改后的衔接和两类游戏的真实验证；不是重写模型或引擎，也不是只改界面文案。当前不据此估算复用百分比或开发工期。

## 7. AI、用户与系统如何分工

| 角色 | 负责什么 |
| --- | --- |
| 用户 | 决定方向、人物风格、场景、玩法感受；确认或提出修改 |
| AI 规划 | 把当前阶段的要求变成任务，读取此前已确认内容，说明需要变动的范围 |
| AI 制作 | 生成素材、制作或修改游戏，交出这一阶段的成果 |
| AI 审查与自动检查 | 判断是否满足当前阶段的要求，发现问题并触发有限修复 |
| 平台流程管理 | 记录用户确认、保存版本、控制下一步能否开始；确认不能由 AI 自行补写 |

人物阶段只检查人物与动作，不要求已经完成整款游戏；场景阶段检查画面组合；核心试玩阶段检查操作；完整游戏和交付阶段才执行完整游玩与导出检查。

已确认内容与新要求冲突时，先向用户说明冲突和影响，再按用户决定执行。一个角色已确认，不代表其外观、能力和用途都允许 AI 任意修改。

## 8. 首版验收

以下是新产品的验收要求，不是本轮已经通过的测试结果。验收必须包含真实模型、真实素材、真实游戏运行，不能只验证按钮或模拟返回。

| 编号 | 验收场景 | 通过标准 |
| --- | --- | --- |
| A01 | 输入“武侠肉鸽” | 给出简短制作约定；可修改；确认前不进入人物生成 |
| A02 | 人物候选与动作 | 可选择人物、提出局部修改、查看真实动作；最终版本被保存 |
| A03 | 等待用户确认 | 人物待确认期间，没有后续场景或玩法生成调用；等待或重开均不自动通过 |
| A04 | 人物与场景衔接 | 场景中使用已确认人物；人物外观、比例与预览一致 |
| A05 | 核心试玩 | 用户能亲自操作；至少完成一条关键行为；不能用视频代替试玩 |
| A06 | AI 持续生成新行为 | 横版加入“落地恢复的二段跳”；俯视加入“剑气碰墙反弹一次”；两者均在游戏里真实生效 |
| A07 | 前面阶段返工 | 修改人物或场景时先展示影响，正确更新相关成果，不改无关规则，旧版可恢复 |
| A08 | 确认与重复操作 | 明确口头确认可继续；“不错但要修改”不通过；重复点击不启动两次；过期版本不能被确认推进 |
| A09 | 中断与失败 | 已确认版本不损坏；失败不推进；重开能恢复阶段，重试不会重复创建无关成果 |
| A10 | 两类完整游戏 | 横版与俯视各完成一个真实项目，包含开始、进展、胜负、暂停和重新开始 |
| A11 | 导出交付 | 实际交付包可运行、文件完整、素材与确认版本一致；通过检查后仍等待用户最终验收 |
| A12 | 小白独立操作 | 在账号和必要环境就绪后，用户不写代码即可完成一次完整制作、一次修改和一次恢复 |

记录每阶段等待时间、实际模型／素材费用、重试次数、人工介入和返工范围，作为下一步比较产品价值的依据。本版不预设未经实测的成功率或生成时长承诺。
